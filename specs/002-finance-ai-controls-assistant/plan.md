## Summary

ControlGuard AI is an AI-assisted internal controls evaluation assistant for finance and audit professionals. Auditors upload process description documents, receive AI-generated candidate control gap findings (structured, evidence-backed, confidence-scored), review each finding with accept/edit/dismiss decisions, and export a finalised PDF audit report. Every action is written to an immutable audit log. Human review of every AI finding is architecturally enforced — no finding reaches a report without an explicit logged acceptance decision.

**Tech stack**: Vue 3 + Vite + Pinia + Tailwind (frontend) · NestJS + Prisma + PostgreSQL (backend) · OpenAI GPT-4o (AI analysis) · pdfkit (report generation)

**Language/Version**: TypeScript 5.x (both frontend and backend)

**Primary Dependencies**:
- Frontend: Vue 3, Vue Router 4, Pinia, Tailwind CSS 3, Axios, Vite
- Backend: NestJS 10, Prisma 5, Passport.js + JWT, multer, pdf-parse, mammoth, openai SDK, zod, pdfkit

**Storage**: PostgreSQL 15 via Prisma ORM

**Testing**: Vitest (frontend components) · Jest (NestJS unit + integration) · Supertest (e2e API tests)

**Target Platform**: Desktop web browser (Chrome/Firefox/Edge) · Node.js 20 server

**Project Type**: Web application — SPA frontend + REST API backend

**Performance Goals**: Complete review session (upload → export) in under 10 minutes for a typical 2-page process document. AI analysis response within 30–60 seconds (OpenAI GPT-4o typical latency).

**Constraints**:
- Session data isolation enforced at API level (403 on cross-user access)
- Audit log entries are insert-only — no update or delete
- Sanitisation step must complete before AI call
- Confidence threshold configurable via environment variable (not hardcoded)
- API key never in client-side code, logs, or version control

**Scale/Scope**: Single-user sessions, prototype quality, no concurrent session handling required

## Implementation Phases

### Phase 1 — Backend Foundation (Sessions, Auth, DB)

Deliver a working NestJS API with authentication, session CRUD, and database connectivity. No AI integration yet. Validates the auth and session state machine end-to-end.

**Tasks**:
1. Initialise NestJS project in `backend/`, configure TypeScript strict mode
2. Set up Prisma with PostgreSQL — write `schema.prisma` from data model
3. Run initial migration, create `PrismaModule` (global singleton)
4. Implement `AuthModule`: login endpoint, JWT strategy, `JwtAuthGuard` as global guard
5. Write seed script (`prisma/seed.ts`) with one test user
6. Implement `AuditLogModule`: `AuditLogService` with `log(event)` method — insert-only
7. Implement `SessionsModule`: create, list, get, finalise endpoints
8. Wire audit log writes into session creation and finalisation
9. Unit tests: `AuthService`, `SessionsService`, `AuditLogService`

**Exit criteria**: `POST /auth/login` returns JWT. `POST /sessions` creates session. `GET /sessions/:id` returns 403 for wrong user. `POST /sessions/:id/finalise` returns 409 when findings pending.

---

### Phase 2 — Document Upload & Sanitisation

Deliver document upload with text extraction and PII sanitisation. Validates the sanitisation component in isolation before it is wired to AI calls.

**Tasks**:
1. Implement `SanitisationService` with regex patterns (email, phone, IBAN/account)
2. Write unit tests for `SanitisationService` with known inputs and expected outputs
3. Implement `DocumentsModule`: multer file upload, type/size validation
4. Wire pdf-parse (PDF) and mammoth (DOCX) for text extraction
5. Store `extractedText`, `sanitisedText`, `wordCount` in `Document` record
6. Write audit log entry (`document_uploaded`) within Prisma transaction
7. Return 400 with clear message on wrong format or oversized file
8. Guard against uploading to a FINALISED session

**Exit criteria**: `POST /sessions/:id/document` with a PDF returns document metadata. Sanitised text in DB does not contain the email address present in the source document. `SanitisationService` unit tests all pass.

---

### Phase 3 — AI Analysis Integration

Deliver AI finding generation with schema validation and governance logging. The raw AI response is stored before parsing. Invalid responses surface as user-facing errors without partial data.

**Tasks**:
1. Write and version the system prompt in `ai-prompt.service.ts` (control framework, output schema, confidence instructions, hallucination mitigation examples)
2. Implement `AnalysisModule`: calls OpenAI with system + user prompt
3. Store system prompt version and user prompt hash in audit log **before** API call
4. Store raw AI response in audit log **before** parsing
5. Validate parsed response against Zod schema (all required fields, valid enums, confidence range)
6. On schema validation failure: log error, return user-facing "Analysis failed" message, preserve raw response
7. Persist validated findings to `Finding` records with `reviewStatus: pending`
8. Transition session status to `ANALYSED` on success
9. Set `requiresHumanReview: true` for findings below `CONFIDENCE_THRESHOLD`
10. Unit tests: `AnalysisService` schema validation (valid response, invalid response, missing evidence excerpt)

**Exit criteria**: `POST /sessions/:id/analyse` stores findings. Findings below threshold have `requiresHumanReview: true`. A deliberately malformed AI response produces a logged error and no findings in the DB.

---

### Phase 4 — Finding Review Workflow

Deliver the accept/edit/dismiss decision flow with all governance constraints enforced.

**Tasks**:
1. Implement `FindingsModule`: `GET /sessions/:id/findings`
2. Implement `POST /sessions/:id/findings/:findingId/review`
3. Enforce: dismiss requires non-empty `reviewerNote`; edited requires `finalRecommendation`
4. Store `ReviewerDecision` with `originalRecommendation` preserved immutably
5. Write `finding_reviewed` audit log entry (in transaction with decision save)
6. Transition `Finding.reviewStatus` to accepted/edited/dismissed
7. Enforce: already-decided findings return 409
8. Enforce: review on a FINALISED session returns 422
9. Unit tests: accept, edit-accept, dismiss (with and without note), re-review rejection

**Exit criteria**: All three decision types save correctly. Dismiss without note returns 400. Re-reviewing a decided finding returns 409. Audit log has one `finding_reviewed` entry per decision.

---

### Phase 5 — Report Export

Deliver the PDF report export with session metadata, accepted findings, and audit trail appendix.

**Tasks**:
1. Implement `ReportsModule`: `GET /sessions/:id/report`
2. Guard: return 422 if session not FINALISED
3. Generate PDF using pdfkit with sections:
   - Cover page: session name, process name, process owner, export date, auditor name
   - Disclosure statement (AI-assisted, human-reviewed)
   - Accepted findings (one section per finding): title, risk, confidence, evidence, final recommendation, reviewer + timestamp
   - Dismissed findings summary: title + justification note
   - Audit trail appendix: table of all log entries for the session
4. Write `report_exported` audit log entry
5. Stream PDF as response with correct Content-Type and Content-Disposition headers
6. Integration test: finalise a session and call report endpoint — verify PDF is returned

**Exit criteria**: `GET /sessions/:id/report` returns a PDF for a finalised session. The PDF contains at least one accepted finding and the audit trail appendix. Returns 422 for non-finalised sessions.

Deliver the complete SPA: login, session management, document upload, review workflow, and report download.

**Tasks**:

**Setup**:
1. Initialise Vue 3 + Vite project in `frontend/`
2. Configure Tailwind CSS, Vue Router, Pinia, Axios

**Auth**:

5. Router guard: redirect unauthenticated users to `/login`
6. Axios interceptor: attach Bearer token; on 401 → clear store + redirect to `/login`

**Sessions**:
7. `SessionsView.vue`: list of sessions with status badges, finding counts, creation dates
8. `NewSessionView.vue`: form to create session (name, process name, process owner)
9. `SessionDetailView.vue`: session metadata + document upload area + analyse button
10. Document upload component: drag-and-drop or file picker, validates type + size client-side

**Review**:
11. `ReviewView.vue`: list of `FindingCard` components ordered by sequence
12. `FindingCard.vue`: displays all finding fields; Accept/Edit/Dismiss action buttons; low-confidence findings have distinct visual treatment (yellow border, flagged badge)
13. `ConfidenceBadge.vue`: colour-coded badge (green/yellow/orange/red) + "Requires Human Review" label when flagged
14. `DismissModal.vue`: required justification text area, validates non-empty before submit

17. `FinaliseView.vue` / finalise button in ReviewView: enabled only when all findings decided

**Component tests**:
20. `FindingCard.vue`: renders low-confidence flag, accept/dismiss buttons
21. `DismissModal.vue`: submit disabled without note, enabled with note
22. `useAuthStore`: token state, checkSession, logout

**Exit criteria**: Full end-to-end workflow completable in the browser. Low-confidence findings have distinct visual treatment. Dismiss without note is blocked in UI. Session cannot be finalised with pending findings (button disabled).

## Key Risks & Mitigations

| Risk | Mitigation |
|---|---|
| OpenAI response schema validation fails | Zod schema + error handling in Phase 3; raw response always preserved |
| Audit log write fails (breaks governance) | Prisma transactions: business op + audit write atomic — both succeed or both fail |
| PII not fully sanitised before AI call | SanitisationService unit tests with known PII patterns; audit log records whether sanitisation ran |
| Token lost on page reload | `GET /auth/me` called on every app mount to rehydrate auth state |
| Finalise allowed with pending findings | Server-side check (not just client-side) in finalise endpoint |
| PDF generation fails | Error logged; user gets clear message; session remains FINALISED and report can be retried |
